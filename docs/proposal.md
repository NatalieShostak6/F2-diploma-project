Попередня робоча назва проєкту
UA: Програмне забезпечення соціальної платформи для обміну контентом із підтримкою асинхронної обробки подій та Real-Time комунікації
EN: Software for a Content-Sharing Social Platform with Asynchronous Event Processing and Real-Time Communication
Робоча назва продукту: Alley
Актуальність та проблематика
Домінуючі платформи обміну візуальним контентом побудовані навколо алгоритмічного ранжування стрічки та рекламної монетизації. Це зміщує модель використання від приватної комунікації у сталому колі контактів до споживання контенту публічних авторів. Сегмент користувачів, для яких соціальна мережа виконує функцію закритого каналу спілкування з обмеженим колом знайомих, лишається недостатньо охопленим. Продуктова відповідь на цю потребу — платформа без алгоритмічної стрічки, рекламних інтеграцій і публічних авторів, з хронологічним відображенням публікацій виключно тих акаунтів, на які підписаний користувач.
Реалізація такої системи ставить п'ять нетривіальних інженерних задач, які й визначають архітектурну складність проєкту.
1. Блокування циклу подій при обробці медіа. Валідація, стиснення, генерація похідних розмірів зображень і санація метаданих — обчислювально витратні операції. Виконання їх синхронно, у межах HTTP-запиту, блокує однопотоковий цикл подій Node.js і спричиняє деградацію часу відгуку всього API під пікове навантаження.
2. Гарантоване відкладене виконання. Механізм тимчасових публікацій із користувацьким часом життя вимагає виконання задачі у заданий момент часу з гарантією доставки. Реалізація на таймерах у пам'яті процесу не переживає перезапуск, а періодичне опитування таблиці публікацій створює постійне паразитне навантаження на СУБД і не забезпечує точності спрацювання.
3. Горизонтальне масштабування Real-Time шару. WebSocket-з'єднання є stateful. При розгортанні кількох екземплярів застосунку подія, згенерована на одному вузлі, не досягає клієнтів, підключених до іншого, без зовнішнього механізму міжпроцесної маршрутизації повідомлень.
4. Неконтрольоване розкриття персональних даних. Зображення, завантажені з мобільних пристроїв, містять у секції EXIF геолокаційні координати, ідентифікатор пристрою та часову мітку зйомки. Збереження файлів без санації метаданих створює канал витоку персональних даних поза відомом користувача.
5. Зв'язність доменних модулів. Публікація поста ініціює множину побічних ефектів: постобробку медіа, інвалідацію кешу стрічок підписників, формування сповіщень. Прямий виклик цих операцій із модуля публікацій формує жорстку зв'язність і робить систему нерозширюваною.
Сформована ідея продукту
Alley — подієво-керована (Event-Driven) серверна платформа обміну медіаконтентом із модульним ядром та трьома незалежно розгортуваними виконавчими процесами:
• HTTP API — синхронний REST-інтерфейс, що обслуговує запити клієнта й публікує доменні події;
• Пул фонових воркерів — споживачі персистентних черг задач, що виконують обробку медіа та відкладене архівування;
• Real-Time шлюз — WebSocket-сервер доставки повідомлень і сповіщень.
Архітектурний стиль — модульний моноліт з асинхронним ядром, спроєктований із чіткими межами доменних модулів для подальшої декомпозиції на мікросервіси. Взаємодія між модулями здійснюється через внутрішню шину подій, довготривалі й відкладені операції винесені у персистентні черги. Клієнтська частина — кросплатформний Progressive Web Application без окремих нативних збірок.
Детальний опис функціоналу (Core Features)
1. Підсистема автентифікації та керування сесіями. Автентифікація за схемою JWT із парою access/refresh-токенів, ротацією refresh-токенів і їх зберіганням у Redis з керованим TTL. Примусове завершення активних сесій. Обмеження частоти запитів за алгоритмом Token Bucket на ендпоінтах входу та реєстрації.
2. Публікація медіаконтенту з асинхронним конвеєром постобробки. Створення публікації з набором до десяти зображень (карусель). Синхронно виконується лише валідація формату та збереження оригіналів; стиснення, генерація похідних розмірів і видалення EXIF-метаданих делегуються черзі задач і виконуються фоновим воркером. Стан публікації відстежується кінцевим автоматом: pending → processing → published → failed.
3. Підсистема динамічного TTL-архівування. Публікація з обраним часом життя (6, 12 або 24 години) породжує відкладену задачу у персистентній черзі. Після настання терміну воркер ідемпотентно переводить публікацію у приватний архів автора. Передбачено відновлювальне сканування при старті застосунку для компенсації задач, пропущених під час простою процесу.
4. Граф соціальних зв'язків і формування стрічки. Односторонні підписки з перевіркою інваріанту не більше 1000 активних підписок на користувача, реалізованою на рівні схеми бази даних. Стрічка формується за стратегією fan-out on read із кешуванням результату в Redis за патерном Cache-Aside та інвалідацією за доменною подією публікації. Посторінкова вибірка реалізована через keyset-пагінацію замість OFFSET.
5. Real-Time обмін повідомленнями. Приватні діалоги з персистентністю історії у реляційній базі, підтвердженням доставки та індикаторами прочитання. Автентифікація сокет-з'єднання виконується за JWT на етапі handshake. Горизонтальне масштабування забезпечує Redis-адаптер, що маршрутизує події між екземплярами WebSocket-шлюзу через механізм Pub/Sub.
6. Шина доменних подій і підсистема сповіщень. Внутрішня шина публікує типізовані доменні події (PostPublished, PostArchived, MessageSent, UserFollowed). Модулі-споживачі підписані на події й не мають прямих залежностей від модуля-джерела. На базі шини реалізовано сповіщення з доставкою у реальному часі та збереженням у базі для офлайн-отримувачів.
7. Контур спостережуваності та адміністрування черг. Структуроване журналювання з наскрізним кореляційним ідентифікатором запиту, ендпоінти перевірки стану (/health, /ready), експорт метрик черг (довжина, час очікування, частка невдалих задач) та панель керування чергами для повторного запуску задач і перегляду черги недоставлених повідомлень.

PostgreSQL (ORM Prisma, версійовані міграції), Redis (черги, кеш стрічки, сесії, Pub/Sub), об'єктне сховище Cloudinary або S3-сумісне MinIO
